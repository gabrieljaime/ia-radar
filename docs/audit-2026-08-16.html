01 Executive assessment

Es un monolito bien diseñado para lo que dice ser: un vertical slice deliberadamente acotado, no un prototipo apurado. La separación determinístico/LLM está bien pensada, la idempotencia de artículos y alertas es sólida gracias a constraints reales de PostgreSQL, y el código es legible y con buena cobertura de tests para su tamaño. El problema no es la ingeniería del pipeline: es que hoy no corre solo (no hay ningún trigger programado en GitHub Actions), que la re-evaluación de un evento cuando aparece mejor evidencia no está implementada aunque el modelo de datos la permite, y que la cobertura de fuentes tiene agujeros grandes y conocidos (Meta, Mistral, xAI, DeepSeek, Qwen no están ni mencionados). Nada de esto exige microservicios ni colas — son huecos puntuales sobre una base correcta.

02 Qué está bien hecho

Separación relevance vs. alert

El LLM sólo explica y puntúa; una función determinística (calculate_scores) decide el score operativo con confidence, trust y hype. No hay doble conteo: relevance queda intacto.

Idempotencia real vía DB

canonical_url único, Alert(event_id, alert_type, channel) único y Digest.idempotency_key único, todos con try/except IntegrityError en el código. Esto protege contra duplicados incluso sin advisory lock.

Perfiles genuinamente dinámicos

load_profiles hace glob("*.yaml") sin asumir cantidad ni slugs. Agregar un perfil es agregar un archivo. Confirmado con test que fuerza un único perfil activo.

1 evento = 1 LLM request

Confirmado en código y en test (test_four_profiles_use_one_llm_request): todos los perfiles activos viajan en una sola llamada.

Auditoría append-only

candidate_records conserva cada ítem recibido, incluso descartes, sin pisar el artículo original. Muy útil para depurar por qué algo no alertó.

Digest sin costo

DigestService no toca RSS ni LLM; lee sólo lo persistido. Cero llamadas nuevas, confirmado leyendo el servicio completo.

Fallos aislados por candidato

Un error de parsing, LLM o Telegram en un ítem no aborta la corrida; se registra y sigue. Buen diseño para un cron desatendido.

Sin over-engineering

No hay colas, cachés, microservicios ni frameworks de agentes. Async sólo donde hay I/O. Esto es exactamente lo apropiado para el volumen real.

Top 5 fuentes a agregar

  1. GitHub Releases de meta-llama, QwenLM/Qwen, deepseek-ai, mistralai. Es la mejora de mayor señal por esfuerzo: API REST estándar (/repos/{org}/{repo}/releases), sin necesidad de scraping ni RSS de terceros. Cierra de un saque el blind spot más grande (Qwen, DeepSeek, Llama, Mistral open-weight releases). Ruido esperado bajo si se apunta a repos de modelo, no a herramientas.
  2. Meta AI Blog (ai.meta.com/blog). Meta hoy no aparece en ningún lado del radar. Requiere un collector web_changelog mínimo (parseo de la lista de posts), no RSS.
  3. xAI — anuncios oficiales de modelo/API. Grok es hoy un blind spot total. Señal esperada media-alta, baja frecuencia.
  4. Mistral changelog (docs.mistral.ai/platform/changelog). Complementa las release de GitHub con cambios de API/plataforma que no siempre generan un release de GitHub.
  5. Cerrar el ciclo de verificación del mirror de Anthropic — no es una fuente nueva, es hacer real el requires_primary_verification que ya existe en el schema.

No pude confirmar URLs de RSS/Atom oficiales para Meta, Mistral, xAI ni Gemini API changelog en la verificación web — no existen o no son estables públicamente. Por eso ninguna de las cinco se propone como type: rss; todas requieren web_changelog o github_releases, salvo la corrección de Anthropic que es pura lógica.

07 Blind spots

Con la configuración actual, esto podría perderse hoy mismo:

  • Un nuevo modelo de Qwen o DeepSeek — ninguna de las dos organizaciones tiene fuente configurada. Ambas han producido releases de impacto global en el último año.
  • Un nuevo Llama de Meta — Meta no está en sources.yaml en absoluto.
  • Un anuncio de Grok/xAI — mismo caso, ausencia total.
  • Un release de API no anunciado en blog (por ejemplo, un cambio silencioso en la API de OpenAI o Google publicado sólo en un changelog técnico) — el radar depende de que la organización decida escribir un post de blog, no monitorea changelogs de API directamente salvo lo que ya cubre Google AI Blog/DeepMind.
  • Un release de GitHub de un modelo open-weight relevante sin cobertura de prensa — no hay collector de GitHub Releases implementado.
  • Un evento con mejor fuente primaria posterior — si la primera cobertura de una noticia viene de un medio secundario y luego la empresa publica el anuncio oficial, el radar ya descartó el segundo artículo como duplicate sin revisar si merece re-análisis (hallazgo P2 de la sección 3).

08 Cost review

El diseño de costo es, en general, el punto más fuerte del proyecto: prefilter determinístico antes de gastar, un LLM request por evento (no por perfil), rate limiter espaciado, y presupuesto configurable en .env. Las recomendaciones de esta auditoría no cambian ese perfil de forma significativa:

  • Agregar GitHub Releases no agrega llamadas HTTP relevantes (la API de GitHub sin auth permite 60 req/hora, más que suficiente para 4 repos revisados cada corrida) ni llamadas LLM adicionales más allá de los eventos genuinamente nuevos que aporte — que es justamente el objetivo.
  • Agregar Meta/Mistral/xAI vía web_changelog agrega HTTP requests baratos (una página por fuente por corrida) pero cero costo LLM extra salvo por eventos reales.
  • Quitar topics/entities del payload LLM (hallazgo P3) reduce tokens de entrada en cada una de las llamadas existentes — la única recomendación que efectivamente baja el costo actual, aunque el ahorro es modesto dado el volumen bajo esperado.
  • El free tier de Gemini (u otro proveedor compatible) debería seguir siendo suficiente: el diseño ya garantiza como máximo unas pocas decenas de llamadas por corrida, incluso agregando 4-5 fuentes nuevas, porque el prefilter sigue siendo la barrera principal antes del LLM.

09 Security review

Token de Telegram: no aparece en ningún log. TelegramAlertChannel.send no loguea la URL completa ni el token; los logs del pipeline (radar_service.py) sólo emiten run_id, contadores y tipos de excepción, nunca el texto del mensaje ni credenciales. El incidente histórico mencionado (URL con token en logs) está corregido en el estado actual del código.

  • Prompt injection: mitigación presente pero mejorable (ver hallazgo P3, sección 3) — mover la política de aislamiento al mensaje system.
  • Source poisoning: el prefilter exige source_trust >= 40 antes de cualquier análisis, y el bypass de "señal amplia de IA" sólo aplica a fuentes con trust_level >= 95 y marcadas primarias — un feed de baja confianza no puede colarse fácilmente al LLM sin pasar por las keywords de perfil.
  • Telegram: HTML-escaping consistente en formatting.py y digest/service.py (título, razones, acciones, URLs vía html.escape(..., quote=True)). Manejo de errores HTTP correcto (response.is_error, payload.get("ok")).
  • Base de datos: sin secretos en el esquema; DATABASE_URL vive sólo en variables de entorno/GitHub Secrets. Constraints únicos actúan como última barrera de idempotencia incluso ante fallos de aplicación.
  • Logging: el JsonFormatter sólo emite campos explícitamente pasados por extra — no hay riesgo de que un objeto completo (incluida una API key) se serialice por accidente vía %s genérico.

  • Advisory lock de PostgreSQL antes de habilitar el cron
  • GitHub Releases collector para meta-llama / Qwen / deepseek-ai / mistralai
  • Actualizar README (conteo de fuentes desactualizado)

Next iteration

  • Re-análisis de evento cuando llega artículo de mayor trust/primario sobre un evento pending o de baja relevancia
  • Job de PostgreSQL en CI (tests.yml) para validar migraciones y constraints reales
  • Collector web_changelog para Meta AI Blog
  • Hacer efectivo (o eliminar) requires_primary_verification

Later

  • Mistral changelog, xAI, Gemini API release notes vía web_changelog
  • Reducir payload LLM de perfiles (quitar topics/entities)
  • Mover política anti-injection al mensaje system
  • Health-check de feeds stale (200 pero sin entradas nuevas en 90 días)

Do not build yet

  • arXiv — el riesgo de ruido supera el valor hasta tener el resto de fuentes primarias cerradas
  • Dashboard, embeddings, research agents, feedback loop automático — coincide con lo que el propio proyecto ya postergó explícitamente
  • Cualquier cola/Redis/Kafka — no hay volumen que lo justifique

11 Final verdict

¿Lo dejaría corriendo solo, todos los días, en su estado actual? Con una condición: primero hay que programarlo — hoy literalmente no corre sin intervención manual.

Una vez agregado el cron, sí lo dejaría funcionando, pero le pondría el advisory lock antes de hacerlo — es la única pieza de "correr desatendido durante meses" que el propio diseño documentado exige y el código no tiene. El resto del sistema — idempotencia de artículos y alertas, aislamiento de fallos, digest sin costo, perfiles dinámicos, separación relevance/alert — está construido con el cuidado correcto para un radar personal que se pretende dejar solo. El agujero real no es de ingeniería del pipeline, es de cobertura: hoy este radar no se entera si Meta, Mistral, xAI, DeepSeek o Qwen lanzan algo, y esas cinco organizaciones producen una fracción significativa de las noticias de IA que probablemente le importan a este usuario. Esa es la brecha que cerraría primero, antes que cualquier feature nueva.
